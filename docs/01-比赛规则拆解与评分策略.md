# 01 · 比赛规则拆解与评分策略

> 这份文档把截图里的规则翻译成“要做的事 + 要留的证据”。所有策略都围绕一句话：**让评委在 10 分钟内相信，这是一个真实、原创、可复现的作品。**

---

## 1. 硬性提交清单（缺一不可）

| 提交物 | 规则要求 | 我们的做法 | 验收方式 |
|---|---|---|---|
| 代码仓库 | GitHub/Gitee，Public 或提供评审权限 | 从 Day 1 开始公开；主分支可读；MIT License | 无痕窗口能打开；评委账号能 clone |
| Git 提交历史 | 完整、细粒度；禁止一次性 `initial commit` 包含全部功能 | 每完成一个模块/一次核心对话提交；40+ 条有意义 commit | `git log --oneline` 能看出演进 |
| Prompt 历史 | 至少 3 个核心功能迭代的完整 Prompt 链：提问、AI 建议、如何引导修 Bug | 建立 `docs/prompt-log/`；每个核心功能一条完整链；截图/录屏 | 抽查任意一条，能对应到 commit |
| README / 复现指南 | 10 分钟极速复现：环境、依赖、环境变量模板 | `README.md` + `REPRODUCE.md`；一条命令启动；演示模式免 Key | 全新目录计时走一遍 |
| 演示视频 | 5–8 分钟，MP4 1080p；至少 2 分钟 AI 协同过程复现 | 真实录屏 + 字幕；包含 Prompt 输入、生成、修复、测试、commit | 完整播放一遍；无黑屏/断音 |
| 技术文档 | PDF，≤30 页；意图控制、架构、可复现性论证 | 18–24 页，图表优先；附录放 Prompt 片段与 schema | 页数、目录、图表、链接检查 |
| 原创性 | 原创作品，禁止直接包装已有开源项目 | 从空仓库搭建；只用基础库；披露第三方依赖 | 依赖清单 + LICENSE + 原创声明 |

### 容易忽略的硬点

- 仓库必须是 **Public**，或者明确给评委访问权限；不要只交一个压缩包。
- `.env` 绝对不能提交；提交 `.env.example`。
- 视频必须是 **MP4 1080p**，不是 MOV/GIF/网盘链接；文件别大到无法上传。
- 技术文档必须是 **PDF**，不是 Markdown/Word；控制在 30 页内。
- Prompt 历史如果工具不支持导出，就用截图/录屏；**截图要能看清 Prompt 和 AI 回复**。
- 提交截止前不要改写 Git 历史；不要在最后一天 force push 覆盖过程。

## 2. 评分维度拆解

### 2.1 过程可复现与演进链路（25%）

评委想看的是：**这个作品不是最后一天“变”出来的，而是一步步长出来的；换一个人，能沿着记录复现。**

| 评分点 | 我们要做的事 | 证据 |
|---|---|---|
| 开发过程真实透明 | 每天提交；提交信息说明“为什么” | commit 时间线、分支/标签、每日进度 |
| Prompt 历史完整 | 3 条以上完整链：目标 → Prompt → AI 建议 → 人工判断 → 修复 → 验证 | `docs/prompt-log/P03.md` 等 |
| 评委可一键复现 | `npm install && npm run dev`；演示模式免 Key | README 计时视频、全新克隆录屏 |
| 代码非拼接 | 模块边界清晰；有测试；能解释关键算法 | 架构图、单测、代码评审记录 |
| 演进路径确定 | 每个版本可回放；快照含 Prompt 版本/模型/种子/哈希 | 复现包、版本历史页 |

**最低动作：**

- Day 1 就建公开仓库，第一条 commit 只放工程骨架和文档，不放大功能。
- 每个功能完成后提交，禁止 `git add .` 一把梭；用 `git add -p` 拆。
- 每条核心 Prompt 存在 `docs/prompt-log/`，包含完整原文与 AI 回复截图。
- 每次成卷保存快照；导出 JSON 里带 `promptVersions`、`model`、`seed`、`hash`。
- `REPRODUCE.md` 写清楚：Node 版本、安装命令、启动命令、演示模式、真实模式、测试命令、常见错误。

### 2.2 解题有效性与实用价值（25%）

评委想看的是：**这是不是真问题？有没有人真的会用？用了之后有没有变好？**

| 评分点 | 我们要做的事 | 证据 |
|---|---|---|
| 痛点定义清晰 | 用教师原话描述“最耗时的一步” | 访谈纪要、原话引用（经同意） |
| 面向真实场景 | 用真实课程大纲跑通，不只用玩具数据 | 真实大纲截图/脱敏文件 |
| 产品闭环完整 | 输入 → 配置 → 生成 → 审校 → 导出 → 回放 | 现场演示 + 任务完成录屏 |
| 有实用价值 | 前后耗时对比；任务完成率；信任度 | 试用记录、指标表 |
| 不是玩具 | 有错误处理、边界、导出、可复现 | 测试报告、失败场景演示 |

**最低动作：**

- Day 3 前完成 2–3 位教师/助教的 20 分钟访谈；没有真人就找有出卷经验的学长/课程助教，但要在文档里如实写明身份。
- 用一位用户的真实大纲（脱敏）跑完整流程；记录从开始到打印的耗时。
- 让用户独立操作一次，不要你在旁边指挥；记录卡点。
- 指标不要编：样本小就写“n=3，初步观察”，不要写“提升 80%”这种没有依据的数字。

### 2.3 方法创新性与意图控制（20%）

评委想看的是：**除了“接个大模型”，你有没有自己的方法？能不能控制 AI 不跑偏？**

我们的三个创新点，必须用“机制”而不是形容词讲：

| 创新点 | 传统做法 | 我们的机制 | 可验证证据 |
|---|---|---|---|
| 蓝图先行 | 一句 Prompt 让 AI 直接出卷 | 教师先定结构；系统分配分值/章节/难度；生成前锁定契约 | 蓝图页、分配算法、覆盖矩阵 |
| 命题契约 | AI 自由发挥，结构漂移 | 每个槽位有 `contractId`、知识点、题型、分值、难度、答案要求；生成后校验 | schema、契约侧栏、合规率 |
| 独立审题 | 让生成模型“自查” | 审题 Agent 不看生成理由，先独立作答，再比对答案，问题必须引用证据 | 审题面板、修复 diff、复审记录 |
| 可回放复现 | 只保存最终文案 | 快照保存全部输入/输出/版本/种子/哈希；回放不调用模型 | 复现包、导入回放、哈希一致 |

**答辩时不要只说“我们用了多 Agent”。** 要说清楚：为什么需要第二个 Agent？因为它和第一个 Agent 的目标函数不同：一个负责“编”，一个负责“挑错”。这叫对抗式校验，不是简单串联。

### 2.4 工程质量与架构设计（15%）

评委想看的是：**代码是不是能维护？有没有严重漏洞？会不会死循环？**

| 评分点 | 我们要做的事 | 证据 |
|---|---|---|
| 模块解耦 | UI / 领域逻辑 / AI 网关 / Prompt 分层 | 目录结构、依赖方向 |
| 数据设计 | Zod schema 单一事实源；版本化迁移 | `src/shared/schemas` |
| 状态管理 | 明确状态机；避免布尔值爆炸 | `pipeline` 状态图 |
| 错误处理 | 超时、重试上限、中断、降级、错误边界 | 失败场景录屏、测试 |
| 安全 | Key 只在服务端；输入限长；XSS 清洗；CSP；限流 | 安全清单、`npm audit` |
| 测试 | 算法单测、schema 测试、主线 E2E | CI 绿灯、覆盖率摘要 |
| 性能 | 懒加载、流式渲染隔离、无死循环 | Lighthouse、性能记录 |

**最低动作：**

- TypeScript `strict: true`；禁止用 `any` 逃逸（确有必要要写注释）。
- 所有跨边界数据（API、localStorage、导入文件）必须过 Zod。
- AI 调用必须有 `AbortController` + 超时 + 最多 1 次修复/重试；禁止无限重试。
- 模型输出当不可信文本处理：Markdown 清洗、不执行 HTML/JS。
- `npm run check` 必须包含 typecheck + lint + unit test；CI 跑 build。
- 至少 1 条 Playwright 主线：载入示例 → 生成 → 审校 → 预览 → 导出。

### 2.5 用户体验与产品精细度（15%）

评委想看的是：**好不好看、顺不顺手、AI 在干活时我知不知道它在干嘛。**

| 评分点 | 我们要做的事 | 证据 |
|---|---|---|
| 界面美观优雅 | 编辑部/纸张风格，区别于通用后台 | 截图、设计 token |
| 交互流畅 | 步骤清晰；不跳页丢状态；自动保存 | 操作录屏 |
| AI 状态友好 | 流式阶段、当前任务、失败可重试、可中断 | Agent 工作台 |
| 细节完整 | 空态、加载、错误、禁用、确认、键盘 | 状态清单 |
| 打印体验 | A4 不截断；试卷/答案分离；页码 | 打印 PDF |
| 响应式 | 1280 / 1024 / 390 三档可用 | 截图 |

**最低动作：**

- 不做“紫色渐变 + 大圆角卡片”的通用 AI 风；用纸白、墨黑、朱砂、宋体建立记忆点。
- 流式状态不要只转圈：显示“正在解析第 3 章”“正在核对第 5 题答案”这类具体状态。
- 错误提示必须告诉用户：发生了什么、能不能重试、数据有没有丢。
- 打印用 `@page` + 专用样式；屏幕上的按钮/侧栏绝不能出现在纸上。

## 3. 评分战术：把分数“做出来”，不是“讲出来”

### 3.1 证据矩阵

从 Day 1 开始维护一张表（模板见 `templates/EVIDENCE_MATRIX.md`）：

| 评分项 | 评委要看到 | 我们的证据 | 位置 | 状态 |
|---|---|---|---|---|
| 过程 25 | 细粒度提交 | 50 条 commit | GitHub Insights | 进行中 |
| 过程 25 | 完整 Prompt 链 | P03 蓝图算法 | `docs/prompt-log/P03.md` | 待补 |
| 实用 25 | 真实用户 | 3 份访谈 | `docs/validation/` | 待做 |
| 创新 20 | 契约机制 | schema + 审题面板 | `src/shared/schemas` | 待做 |
| 工程 15 | 测试 | CI 绿灯 | Actions | 待做 |
| UX 15 | 流式状态 | 录屏 01:40 | 视频 | 待做 |

**提交前，这张表不允许有“待做”。**

### 3.2 三条核心 Prompt 链（建议）

不要随便找三条“你好/帮我写代码”。选有冲突、有判断、有修复的：

1. **蓝图分配算法**：AI 第一版平均分配 → 你发现章节权重和分值取整冲突 → 引入最大余数法 → 加边界测试 → 覆盖矩阵偏差从 8 分降到 1 分。
2. **结构化输出修复**：模型返回带 Markdown 代码块的 JSON / 被截断 → Zod 校验失败 → 设计“提取 + 一次修复 + 原始输出可下载” → SSE 断流不再白屏。
3. **审题体验迭代**：第一版只显示“风险高/中/低” → 你发现教师不敢信 → 改成“独立答案 + 证据引用 + 修复 diff” → 用户试用时能在 2 分钟内处理完。

每条链都要有：**原始 Prompt、AI 首轮方案、你的判断、第二轮 Prompt、最终 diff、测试/验收、commit。**

### 3.3 演示的“双保险”

- **主演示**：本地/部署环境，演示模式，不依赖网络和 API Key。
- **备份**：完整录屏 + 导出的复现包；现场接口挂了直接放录屏，并说明“这是同一版本的录屏，复现包在这里”。

不要在现场赌 API 延迟。评委不会因为你“网络不好”而加分。

## 4. 失分/ disqualification 风险清单

| 风险 | 后果 | 规避 |
|---|---|---|
| 直接套用开源后台模板 | 原创性存疑，直接出局 | 从空仓库搭；只用基础库；关键页面自己设计 |
| 最后一天一个 `initial commit` | 过程分几乎清零 | 每天提交；功能完成即提交 |
| Prompt 记录缺失/只有截图一角 | 无法证明 AI 协作过程 | 完整 Prompt 原文 + 回复 + commit 对应 |
| 伪造用户数据/提交时间 | 诚信问题，严重扣分 | 没有就写“未验证”；保留真实时间戳 |
| 视频里只有 PPT/录屏配音 | AI 协同分不足 | 至少 2 分钟真实操作：输入 Prompt、AI 生成、修复、测试 |
| 技术文档超过 30 页/不是 PDF | 形式不合规 | 18–24 页；提前导出 PDF 检查 |
| 仓库私有/链接失效 | 评委无法查看 | 无痕窗口 + 评委账号双验证 |
| API Key 泄露 | 安全漏洞 + 费用风险 | 服务端环境变量；`.gitignore`；提交前扫描 |
| 现场演示依赖外网 | 演示失败 | 演示模式 + 备份录屏 + 本地快照 |
| 功能太多但都是半成品 | 闭环不成立 | P0 冻结；宁少一个功能，不少一个验收 |

## 5. 选题决策：为什么是题衡

我们对比过三类容易“看起来厉害”的方向：

| 方向 | 优势 | 风险 | 结论 |
|---|---|---|---|
| 多 Agent 协同看板 | 视觉强、AI 味足 | 同质化严重；没有真实业务闭环容易变玩具；API 依赖高 | 不作为主赛道 |
| 3D 数字孪生/具身仿真 | 现场冲击力强 | 开发风险高；内容正确性难保证；7 天难打磨 | 放弃 |
| AI 命题/组卷工作台 | 真痛点、闭环清晰、确定性部分可测试、演示变化强 | 需要真实教师验证；内容质量要严控 | **选择** |

题衡的独特性不在“AI 会写字”，而在：

- **结构先于内容**：蓝图和契约是确定性资产，AI 只是填充器。
- **审查先于信任**：独立作答 + 证据 + 教师终审。
- **复现先于炫技**：每个版本可回放，评委可检查。

这三句话，就是技术文档和答辩的主线。

## 6. 目标分数与取舍

| 维度 | 保守目标 | 冲刺目标 | 如果时间不够，保什么 |
|---|---:|---:|---|
| 过程可复现 | 22 | 25 | 保提交频率 + Prompt 链 + 复现指南 |
| 解题有效性 | 20 | 24 | 保 2 位真实用户 + 一条真实大纲 |
| 方法创新 | 16 | 19 | 保蓝图/契约/审题三个机制讲透 |
| 工程质量 | 12 | 15 | 保确定性算法测试 + 无高危漏洞 |
| 用户体验 | 12 | 15 | 保主线视觉 + 流式状态 + 打印 |
| **合计** | **82** | **98** | 先保 82，再冲长板 |

> 不要为了冲“创新”去加无法验证的 Agent 数量。**一个能被解释、被测试、被复现的机制，胜过十个演示不出来的概念。**
