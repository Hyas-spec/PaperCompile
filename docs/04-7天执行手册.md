# 04 · 7 天执行手册

> 这份手册假设你每天能投入 **6–8 小时**，一个人开发。
> 如果每天只有 2–3 小时：把 7 天拉成 12–14 天，顺序不变。
> 如果只剩 72 小时：直接看第 9 节，严格砍功能。

---

## 0. 开工前 30 分钟

- [ ] 安装 Node.js 20+（当前机器 v24 可用）和 Git。
- [ ] 注册 GitHub/Gitee，新建 **Public** 仓库，先不要勾选 README/模板。
- [ ] 设置真实 Git 身份：

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

- [ ] 安装编辑器（VS Code / Cursor 均可），登录。
- [ ] 打开录屏工具（Windows：`Win + G`），测试麦克风和系统声音。
- [ ] 建一个 `docs/prompt-log/` 目录（P01 会建），准备记录每次核心 Prompt。
- [ ] 给 2–3 位教师/助教发试用邀请，约在 Day 3–5。
- [ ] 准备一个 OpenAI 兼容 API Key（可选；没有也能做演示模式）。
- [ ] 把手机静音，关掉无关聊天窗口。**接下来 7 天，只做这一件事。**

---

## 1. 每天的节奏

不要从早写到晚。用 4 个 90 分钟工作块，中间休息：

| 块 | 时间 | 内容 |
|---|---|---|
| A | 09:00–10:30 | 最难的核心功能（算法/Agent/架构） |
| B | 11:00–12:30 | 继续核心功能 + 测试 |
| C | 14:00–15:30 | UI/联调/修复 |
| D | 16:00–17:30 | 验收、提交、文档、记录证据 |

**每天固定动作：**

1. 开头读 `CURRENT_STATE.md`，写下今天 3 个必须完成的结果。
2. 每个功能开始前，从 `05-提示词库.md` 复制对应 Prompt。
3. 功能完成后：手动验收 → `npm run check` → 提交 → 更新 `CURRENT_STATE.md` → 截屏/录屏。
4. 收工前 `git status` 必须干净；写下明天第一件事。

> 不要“先写一天，最后一起提交”。**提交是过程证据，不是收尾动作。**

- [ ] `npm run check` 通过（typecheck + lint + 测试；测试可以先很少）。

- [ ] 没有引入成品后台模板；设计 token 已落地。

### 卡住了怎么办

- 端口冲突：改 `PORT`，不要杀未知进程。
- Express middleware 不工作：先用 Vite 默认 dev server + 代理，保证能跑；Day 2 再合并单端口。
- Tailwind 配置报错：锁 3.4.x，删掉 v4 语法；不要在此卡超过 30 分钟。
- 设计没灵感：先做“纸白 + 墨黑 + 宋体标题 + 细线”，不要加渐变。

- [ ] 至少 6 条真实 commit。

### 卡住了怎么办

- 分配算法出现负剩余/死循环：先限制最大迭代次数，打印每一步；回到“最大余数 + 贪心”的最简版本。
- 权重取整对不上：允许偏差，但必须显示；不要为了“完美”引入复杂优化器。
- 表单状态混乱：把蓝图表单改成受控 + Zod 校验，一次只维护一个 `blueprint` 对象。

### 提示词

### 建议提交

```text

```

### 必须留下的证据

- 一次真实 API 解析成功的截图（如果暂时没有 Key，可延后，但 Day 4 前必须验证一次）。
- 一次错误/重试的截图（比如故意填错 Key）。
- Prompt 日志：`P05` 的完整链。

### 关门条件

- [ ] 无 Key 自动进入演示模式，界面有清晰徽标。
- [ ] 演示模式不发外部请求（Network 面板可验证）。
- [ ] 真实模式 Key 只在服务端，前端 bundle 搜不到。
- [ ] SSE 能逐段显示状态；中断按钮有效。
- [ ] 模型返回坏 JSON 时，有修复/报错，不白屏。
- [ ] 错误提示可读，数据不丢。
- [ ] 至少 6 条真实 commit。

### 卡住了怎么办

- SSE 被缓冲：设置 `Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no`，每 15s 心跳。
- CORS：同源代理，不应该有 CORS；如果从 Vite 直连模型，立刻改回服务端。
- 没有 API Key：先把演示模式做完整，真实模式留到 Day 4 上午；不要卡住主线。
- JSON 解析失败：不要加正则“猜”；用“提取平衡括号 + Zod + 一次修复 + 原始输出下载”。

## 5. Day 4：出题、审题、审校

**目标：** 10 道题全部有契约、答案、审题结果；能定向修复。

### 任务

| 时间 | 任务 | 产出 |
|---|---|---|
| 0:00–1:30 | P06：命题 Agent，按 section 批量生成 | 10 道题 |
| 1:30–3:00 | P07：审题 Agent + 独立作答 + 问题 schema | 每题有审题 |
| 4:00–5:30 | 修复循环 + 最多 2 轮 + 失败标记 | 定向修复可用 |
| 5:30–6:30 | P08 基础审校台：列表/详情/通过/锁定 | 可处理问题 |
| 6:30–7:00 | 联调、提交 | 6+ 条 commit |

### 提示词

- `P06` 命题 Agent 与批量生成
- `P07` 审题 Agent 与定向修复
- `P08` 审校工作台（可拆成两次）

### 建议提交

```text
feat(agent): generate contract bound questions in batches
feat(agent): add independent review with evidence based issues
feat(agent): repair only flagged issues with max two rounds
feat(review): add question list detail and status actions
fix(ai): handle partial generation failure without losing data
```

### 必须留下的证据

- 一张“题目详情 + 契约侧栏 + 审题证据”的截图。
- 一段“修复前后 diff”的录屏。
- 一次“某题生成失败，其他题继续”的测试。
- Prompt 日志：`P07` 的完整链（重点：如何引导 AI 修 JSON/审题问题）。

### 关门条件

- [ ] 10 道题全有 contractId、答案、解析、评分点。
- [ ] 每题有审题结果；问题有 evidence，不是空话。
- [ ] 修复只改被指出部分；最多 2 轮；失败标记“需人工”。
- [ ] 可通过/锁定/编辑；锁定后 AI 不覆盖。
- [ ] 单题失败不阻塞整卷。
- [ ] 至少 6 条真实 commit。

### 卡住了怎么办

- 生成太慢：按 section 批量（3 次调用），并发限制 2；不要一题一次。
- 模型总超纲：把契约的 `forbidden`/`mustCover` 写具体；生成后做关键词/引用校验；不要只靠 Prompt。
- 审题官“什么都通过”：让它先独立作答，并把 `independentAnswer` 必填；提高 temperature 到 0.3 试试。
- 审题官“什么都报错”：只允许 blocker/major/minor 三档，要求 evidence 引用原文；过滤无证据问题。
- 审校台做不完：先做列表 + 详情 + 通过/锁定；diff/筛选可以 Day 6 补。

## 10. 怎么跟 AI 协作（重要）

### 10.1 一次只做一件事

不要一次粘贴 P01–P05。AI 会“顺手”做一堆你没验收的东西，最后难以定位。

**正确节奏：**

```text
复制一个 Prompt
→ AI 给计划
→ 你确认/修正
→ AI 实现
→ 你手动验收
→ npm run check
→ 提交
→ 更新 CURRENT_STATE
→ 下一个 Prompt
```

### 10.2 先计划，后写代码

大功能（P04/P05/P07/P09）先让 AI 输出：

- 要改哪些文件；
- 数据流怎么走；
- 验收标准；
- 风险点。

你确认后再让它写。这样能避免“写了一堆，方向错了”。

### 10.3 每次给足上下文

新会话开头：

```text
先读 PROJECT.md、CURRENT_STATE.md、docs/03-技术方案与架构.md，
再读本次任务对应的 Prompt。不要凭记忆猜。
```

### 10.4 不要让 AI 自评“完成了”

AI 说“已完成”不算。你必须：

- 自己点一遍；
- 看 Network/Console；
- 跑测试；
- 试一个失败场景；
- 看 diff 有没有无关改动。

### 10.5 保护你的提交历史

- AI 改完，先 `git diff` 看一遍。
- 不要 `git add .` 一把梭；按模块拆。
- 不要为了让历史“好看”而伪造时间/作者。
- 每次提交信息写“为什么”，不是“改了什么”。

### 10.6 记录 Prompt

每个核心功能至少记录：

- 完整 Prompt 原文；
- AI 首轮建议（截图/摘要）；
- 你发现的问题；
- 第二轮 Prompt；
- 最终 diff / commit；
- 测试结果。

> 比赛要求至少 3 个核心迭代。建议做 5 个，选最好的 3 个提交。

## 11. Bug 修复协议

### 11.1 先复现，再提问

给 AI 的信息必须包含：

```text
现象：
复现步骤：
期望：
实际：
错误日志/截图：
最近改动：
相关文件：
约束：不要重构无关模块。
```

### 11.2 先根因，后修复

```text
先不要改代码。请根据日志和代码定位根因，
给出最多 3 个可能原因，并说明如何验证。
确认根因后，再给最小修复方案。
```

### 11.3 修复必须带回归测试

- 修一个 bug，加一个测试。
- 测试先失败，再通过。
- 提交信息写 `fix(...)`，body 写根因。

### 11.4 30 分钟原则

- 30 分钟没有进展：回滚到上一个可用 commit。
- 不要在一个 bug 上耗掉半天；先绕过，记录到 `KNOWN_ISSUES.md`。
- 演示前 24 小时，只修阻断问题，不做重构。

## 12. 功能冻结规则

**Day 6 结束（或提交前 24 小时）冻结。**

冻结后允许：

- 修 P0 bug；
- 改文案/间距/颜色；
- 补文档/视频；
- 修测试。

冻结后禁止：

- 新页面/新功能；
- 换框架/换状态库；
- 大改数据模型；
- 重构核心算法；
- 加动画/特效（除非 5 分钟内完成且不影响稳定）。

新想法写到 `IDEAS.md`，答辩时可以讲“下一步”，不要现在做。
